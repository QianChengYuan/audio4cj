# cjlint 项目级配置

本目录存放 audio4cj 的 `cjlint` 静态检查配置。目标是让 lint 输出**只含真实问题**
—— 一个总在报噪声的门禁，等于没有门禁。

## 使用方式

在项目根目录执行：

```bash
cjlint -f src/ -c .
```

`-c .` 指向项目根，cjlint 会读取本目录的 `cjlint_rule_list.json`，
因此**不会污染**该机器上其它仓颉项目的全局配置。

CI（`.github/workflows/ci-lint.yml`）使用完全相同的命令，本地与线上口径一致。

## 配置的由来与校准

初始白名单沿用了同机另一个仓颉项目（CJQT6）的配置 —— 那是一份**已验证可用**的
规则集，比从零拼装更可靠。但它为 Qt 封装库的命名习惯额外屏蔽了
`G.NAM.03/04/05`（Qt 采用 PascalCase 枚举值等）与 `G.OPR.01`。

audio4cj 遵循标准仓颉命名，没有这些约束，因此把这几条**恢复启用并实测**：

| 规则 | 恢复后实测 | 处置 |
|---|---|---|
| `G.NAM.03` / `G.NAM.04` / `G.NAM.05` | 0 条 | 保持启用（继承的屏蔽与本项目无关） |
| `G.OPR.01` | 0 条 | 保持启用 |

结论：**不沿用与本项目无关的屏蔽**。当前启用 52 条规则，`src/` 实测 0 条告警。

## 屏蔽的规则及原因

只有 3 条规则被屏蔽，每条都有明确的项目级理由：

| 规则 | 屏蔽原因 |
|---|---|
| `G.NAM.01` | **误报**。该规则要求包名与目录名对应，但只识别单段包名；本项目使用多段包名 `audio4cj.meta` / `audio4cj.core` 等，这是仓颉合法且推荐的命名方式 |
| `G.PKG.01` | **有意为之**。该规则建议避免 `import std.collection.*` 这类通配符导入；本项目在内部实现层统一使用通配符以保持导入段落简洁，而这些属模块内可见的实现，不构成公开 API 面 |
| `G.FUN.01` | **语义主观**。该规则建议单函数不超过 50 行；本项目的解析函数（如 `oggFirstPackets`、`mp4ApplyItem`）是「一段完整的格式解析流程」，拆开反而会切断上下文、需要额外传递中间状态 |

## 待办：`G.ERR.01`（暂缓启用）

`G.ERR.01` 要求 `throw` 所在函数的文档注释写明可能抛出的异常类型。
实测本项目有 **27 处**未标注。该规则**当前被屏蔽**，但这是一项**待办**而非
「不适用」—— 本项目最核心的契约之一就是「错误一律用异常表达」，
把异常类型写进 API 文档与这一契约方向完全一致。

**暂缓的理由**：这 27 处多为内部守卫（如已关闭资源上的 `ClosedResourceException`），
其中相当一部分的异常语义已在**类级文档**中说明；逐处补齐需要确认每个函数
实际的抛出集合，适合作为独立的清理工作，不宜与首次发布混在一起。

补齐后，把 `"G.ERR.01"` 加回 `cjlint_rule_list.json` 的 `RuleList` 即可启用。

## 恢复某条被屏蔽的规则

把规则名加回 `cjlint_rule_list.json` 的 `RuleList` 数组即启用；删除即屏蔽。
恢复后应**先实测告警数量**，再决定是修代码还是保留屏蔽 ——
本文件的两张表格就是这套流程的产物。

## 与 `cjpm build -l` 的关系

`cjpm build -l` 内部调用 `cjlint` 时使用**全局配置**
（`<cangjie-home>/tools/config/cjlint_rule_list.json`），不支持指向项目内配置。因此：

- 项目 lint 统一用 `cjlint -f src/ -c .`（本地与 CI 一致、可版本化）；
- **不要**为了让 `cjpm build -l` 干净而改全局配置 —— 那会影响该机器上所有仓颉项目。
